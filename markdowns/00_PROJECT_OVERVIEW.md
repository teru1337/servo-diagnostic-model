# 00_PROJECT_OVERVIEW.md

# Общее описание проекта Servo Diagnostic Model

## 1. Назначение документа

Этот документ является входной точкой для разработки Python-проекта `servo_diagnostic_model`.

Цель документа — объяснить coding agent, что именно нужно реализовать, зачем это нужно и какие ограничения необходимо соблюдать при разработке.

Проект НЕ является задачей по созданию большой нейросети, LLM или модели глубокого обучения. Нужно реализовать с нуля физико-статистическую диагностическую модель для анализа телеметрии сервопривода.

Модель должна быть:

- интерпретируемой;
- модульной;
- пригодной для интеграции в backend/PWA-платформу;
- работающей на малом количестве данных;
- не зависящей от готовых ML-моделей из `sklearn`, `tensorflow`, `pytorch`;
- способной выдавать не только числовую оценку, но и объяснение результата.

---

## 2. Контекст проекта

Проект относится к платформе ServoAI Dashboard.

ServoAI Dashboard — это цифровая PWA-платформа для мониторинга, диагностики, прогнозирования и управления сервоприводом. В более широкой архитектуре система включает:

1. Сервопривод.
2. Edge-уровень сбора данных.
3. Backend/API.
4. Хранилище телеметрии.
5. Диагностический или AI-модуль.
6. PWA-клиент для оператора или инженера.

Разрабатываемая модель относится к диагностическому/AI-модулю, но в данной версии она не должна быть большой нейросетевой моделью. Это должна быть физико-статистическая модель, которая работает с телеметрией и выдаёт инженерно понятную оценку состояния привода.

---

## 3. Объект диагностики

Объект диагностики — электрический сервопривод Delta ASDA-B3-E или совместимая модель сервопривода, передающая телеметрию в похожем формате.

Система анализирует параметры:

- состояние CiA 402;
- `statusword`;
- режим работы;
- положение;
- скорость;
- момент;
- ток;
- напряжение DC-шины;
- температуру;
- коды ошибок;
- паспортные ограничения.

В рамках MVP допустимо работать как с реальной телеметрией, так и с демонстрационными/эмуляционными данными.

---

## 4. Главная задача модели

Главная задача — по окну телеметрии определить техническое состояние сервопривода.

Модель должна принимать не одну строку данных, а временное окно, например последние 5 секунд телеметрии.

На основе этого окна модель должна рассчитать:

- инженерные признаки;
- физические риски;
- статистические отклонения;
- Health Score;
- Anomaly Score;
- итоговое состояние;
- основные причины результата;
- рекомендации для оператора или инженера.

---

## 5. Концепция модели

Модель называется физико-статистической, потому что она объединяет два подхода.

### 5.1. Физический подход

Физический подход использует инженерные ограничения и паспортные пределы оборудования.

Примеры:

- ток не должен приближаться к номинальному или максимальному значению;
- момент не должен быть близок к предельному значению;
- скорость не должна превышать допустимый диапазон;
- температура не должна расти до критической зоны;
- напряжение DC-шины не должно уходить в область перенапряжения или просадки;
- `error_code != 0` является признаком аварийного или нештатного состояния;
- флаги `Fault` и `Warning` в `statusword` должны влиять на итоговое состояние.

Физический блок отвечает на вопрос:

> Насколько текущий режим близок к опасным физическим или паспортным ограничениям?

---

### 5.2. Статистический подход

Статистический подход сравнивает текущее поведение привода с нормальным профилем.

Примеры:

- ток не превышает номинал, но стал нетипично высоким для режима удержания;
- напряжение DC-шины находится в допустимом диапазоне, но стало заметно менее стабильным;
- скорость не превышает предел, но появились микроколебания;
- температура ещё безопасная, но растёт быстрее обычного;
- связь между током и моментом изменилась относительно нормальной работы.

Статистический блок отвечает на вопрос:

> Насколько текущее поведение отличается от нормального поведения в таком же режиме работы?

---

## 6. Почему не используется готовая ML-модель

В рамках текущей версии проекта НЕ нужно подключать готовые ML-модели из библиотек:

- `sklearn`;
- `tensorflow`;
- `pytorch`;
- `keras`;
- `xgboost`;
- `lightgbm`;
- `catboost`.

Причины:

1. Данных мало.
2. Аварийных и предаварийных режимов может не быть.
3. Для учебного проекта и статьи важна объяснимость.
4. Инженерная диагностика должна показывать вклад каждого параметра.
5. Модель должна быть реализуема с нуля и понятна проверяющему.

Разрешается использовать:

- стандартную библиотеку Python;
- `math`;
- `statistics`;
- `json`;
- `dataclasses`;
- `typing`;
- `pathlib`;
- `datetime`;
- `csv`;
- `sqlite3`;
- `numpy`;
- `pandas`.

`numpy` и `pandas` разрешены для математики и обработки таблиц, но не для использования готовых ML-алгоритмов.

## 7. Что модель должна принимать на вход

Базовый вход модели — окно телеметрии.

Окно телеметрии — это список сэмплов за ограниченный промежуток времени.

Пример:

- окно: 5 секунд;
- шаг окна: 1 секунда;
- частота телеметрии: около 10 Гц;
- количество точек в окне: около 50.

Один сэмпл может содержать следующие поля:

- `ts`;
- `t`;
- `device_id`;
- `statusword`;
- `mode_display`;
- `position`;
- `velocity`;
- `torque`;
- `torque_Nm`;
- `current`;
- `current_A`;
- `dc_bus_voltage`;
- `drive_temp`;
- `error_code`;
- `rated_current`;
- `rated_torque`;
- `max_velocity`.

Подробная схема данных описана в файле:

```text
02_TELEMETRY_SCHEMA.md
```

## 9. Основные состояния модели

Модель должна классифицировать состояние в одну из четырёх категорий.

### 9.1. `normal`

Нормальное состояние.

Признаки:

- Health Score высокий;
- Anomaly Score низкий;
- ошибки отсутствуют;
- температура нормальная;
- DC-шина стабильна;
- ток и момент не приближаются к предельным значениям.

---

### 9.2. `observation`

Состояние наблюдения.

Признаки:

- прямой аварии нет;
- параметры пока находятся в допустимом диапазоне;
- один или несколько признаков начали отклоняться от нормы;
- оператору или инженеру стоит обратить внимание на динамику.

Пример:

- слегка растёт температура;
- ток стал выше обычного;
- напряжение стало менее стабильным;
- появились слабые микроколебания.

---

### 9.3. `warning`

Предупреждение.

Признаки:

- параметры заметно приблизились к опасной зоне;
- статистическая аномалия выражена;
- есть риск перегрева, перегрузки, нестабильности питания или механической проблемы;
- рекомендуется проверка оборудования или снижение нагрузки.

---

### 9.4. `critical`

Критическое состояние.

Признаки:

- `error_code != 0`;
- `statusword` содержит Fault;
- Health Score ниже критического порога;
- Anomaly Score очень высокий;
- температура, ток, момент или DC-шина находятся в опасной зоне.

В критическом состоянии модель должна выдавать приоритетную рекомендацию и явно указывать причину.

---

## 10. Что НЕ нужно делать в первой версии

В первой версии НЕ нужно реализовывать:

- глубокую нейросеть;
- автоэнкодер;
- прогноз RUL;
- LLM-рекомендации;
- подключение к реальному приводу;
- полноценный backend;
- WebSocket;
- PWA-интерфейс;
- авторизацию;
- управление приводом;
- запись команд в привод.

Первая версия должна сфокусироваться на диагностическом ядре.

## 11. Что нужно сделать в первой версии

Первая версия должна включать:

1. Загрузку телеметрии из CSV.
2. Проверку схемы данных.
3. Предобработку.
4. Разделение на окна.
5. Расчёт признаков.
6. Расчёт физических рисков.
7. Расчёт Health Score.
8. Простую классификацию состояния.
9. Формирование объяснения.
10. Формирование рекомендаций.
11. Возврат результата в JSON-совместимом формате.

Статистический Anomaly Score можно добавить во второй версии, но архитектуру нужно подготовить заранее.

## 13. Главный принцип реализации

Проект должен быть написан модульно.

Нельзя писать всю логику в одном файле.

Каждый этап должен быть отдельным модулем:

- загрузка данных;
- валидация;
- оконная обработка;
- признаки;
- физические риски;
- статистические риски;
- Health Score;
- классификация;
- объяснение;
- рекомендации;
- тесты.

---

## 14. Ожидаемый результат от coding agent

Coding agent должен реализовать Python-пакет:

```text
servo_diagnostic_model/
```

Пакет должен позволять выполнить диагностику телеметрии командой или функцией верхнего уровня.

Пример использования:

```python
from servo_diagnostic_model.api.diagnostic_service import diagnose_csv

result = diagnose_csv(
    csv_path="data/telemetry.csv",
    limits_path="config/limits.json",
    weights_path="config/weights.json",
    thresholds_path="config/thresholds.json"
)

print(result)
```

Результат должен быть JSON-совместимым словарём или списком словарей по каждому окну.

## 15. Критерии готовности первой версии

Первая версия считается готовой, если:

1. Проект запускается без ошибок.
2. CSV-файл телеметрии загружается.
3. Данные проходят валидацию.
4. Данные разбиваются на окна.
5. Для каждого окна считаются признаки.
6. Для каждого окна считаются физические риски.
7. Для каждого окна считается Health Score.
8. Для каждого окна определяется состояние.
9. Для каждого окна формируются объяснения.
10. Для каждого окна формируются рекомендации.
11. Результат можно сохранить в JSON.
12. Есть минимум несколько unit-тестов.
13. Код разделён по модулям.
14. Нет использования готовых ML-моделей.
