# 03_MODEL_REQUIREMENTS.md

# Требования к физико-статистической диагностической модели

## 1. Назначение документа

Этот документ описывает требования к диагностической модели как к программному и инженерному модулю.

Coding agent должен использовать этот документ как техническое задание.

Документ отвечает на вопросы:

- что модель должна принимать;
- что модель должна возвращать;
- какие состояния должна определять;
- какие ограничения должны соблюдаться;
- что считается корректной работой;
- какие ошибки нужно обрабатывать;
- какие функции должны быть доступны для дальнейшей интеграции.

---

## 2. Цель модели

Цель модели — по окну телеметрии сервопривода определить техническое состояние оборудования и сформировать объяснимое диагностическое заключение.

Модель должна преобразовать данные по цепочке:

```text
Telemetry Window
    ↓
Features
    ↓
Physical Risks
    ↓
Statistical Anomaly Score
    ↓
Health Score
    ↓
State Classification
    ↓
Explanation
    ↓
Recommendations
```

В первой версии допускается реализовать статистическую часть как заглушку с нулевым Anomaly Score, но архитектура должна предусматривать её подключение.

---

## 3. Основные принципы

### 3.1. Интерпретируемость

Каждый результат должен быть объяснимым.

Если Health Score снизился, модель должна показать, какие компоненты внесли вклад:

- ток;
- момент;
- скорость;
- температура;
- DC-шина;
- ошибки;
- `statusword`;
- статистическое отклонение;
- качество данных.

---

### 3.2. Инженерная применимость

Модель должна использовать физический смысл параметров.

Пример:

```text
Высокий ток при разгоне может быть нормой.
Высокий ток при удержании может быть признаком механической проблемы.
```

Поэтому модель должна учитывать фазы движения и режимы работы хотя бы на базовом уровне.

---

### 3.3. Работа на малом наборе данных

Модель должна работать даже при наличии одной короткой сессии телеметрии.

Нельзя требовать:

- тысячи размеченных аварий;
- длительного обучения;
- GPU;
- больших нейросетевых моделей.

---

### 3.4. Модульность

Каждая часть модели должна быть отделена:

- data loading;
- validation;
- windowing;
- feature extraction;
- physical risks;
- statistical profile;
- anomaly score;
- health score;
- classification;
- explanation;
- recommendations.

---

### 3.5. Расширяемость

Модель должна быть написана так, чтобы позже можно было добавить:

- SQLite loader;
- FastAPI endpoint;
- WebSocket output;
- сохранение результатов в PostgreSQL;
- расширенный декодер CiA 402;
- более сложный Anomaly Score;
- автоэнкодер;
- LLM-рекомендации.

Но первая версия не должна зависеть от этих компонентов.

---

## 4. Вход модели

### 4.1. Основной вход

Основной вход — временное окно телеметрии:

```python
list[TelemetrySample]
```

или таблица:

```python
pandas.DataFrame
```

Внутри проекта лучше привести всё к единому представлению.

Рекомендуемый внутренний формат:

```python
list[TelemetrySample]
```

или

```python
TelemetryWindow
```

---

### 4.2. TelemetryWindow

Желательно создать отдельную структуру:

```python
@dataclass
class TelemetryWindow:
    samples: list[TelemetrySample]
    start_t: float
    end_t: float
    device_id: str | None
    sampling_rate_hz: float | None
```

---

### 4.3. Конфигурации

Модель также должна принимать конфигурации:

1. `limits.json`
2. `weights.json`
3. `thresholds.json`

Эти файлы описаны подробнее в будущих документах.

Минимально нужно предусмотреть:

```python
limits: dict
weights: dict
thresholds: dict
```

---

## 5. Выход модели

Модель должна возвращать JSON-совместимый словарь.

### 5.1. Основная структура результата

```json
{
  "window_start": 0.0,
  "window_end": 5.0,
  "device_id": "servo_1",
  "health_score": 92.5,
  "anomaly_score": 0.12,
  "state": "normal",
  "risk_level": "low",
  "motion_phase": "holding",
  "features": {},
  "risks": {},
  "main_causes": [],
  "explanation": [],
  "recommendations": [],
  "data_quality": {},
  "debug": {}
}
```

---

### 5.2. Поле `health_score`

Тип:

```text
float
```

Диапазон:

```text
0..100
```

Смысл:

- 100 — идеальное состояние;
- 0 — максимально плохое состояние.

Health Score должен уменьшаться при росте рисков.

---

### 5.3. Поле `anomaly_score`

Тип:

```text
float
```

Диапазон:

```text
0..1
```

Смысл:

- 0 — поведение полностью похоже на нормальное;
- 1 — поведение сильно аномальное.

В версии 0.1 можно возвращать:

```json
"anomaly_score": 0.0
```

если статистический профиль ещё не реализован.

---

### 5.4. Поле `state`

Тип:

```text
str
```

Допустимые значения:

```text
normal
observation
warning
critical
unknown
```

`unknown` использовать только если данных недостаточно для диагностики.

---

### 5.5. Поле `risk_level`

Тип:

```text
str
```

Допустимые значения:

```text
low
medium
high
critical
unknown
```

`risk_level` может быть связан со `state`, но не обязан полностью совпадать.

Рекомендуемое соответствие:

| `state`       | `risk_level` |
| ------------- | ------------ |
| `normal`      | `low`        |
| `observation` | `medium`     |
| `warning`     | `high`       |
| `critical`    | `critical`   |
| `unknown`     | `unknown`    |

---

### 5.6. Поле `motion_phase`

Тип:

```text
str
```

Допустимые значения:

```text
holding
acceleration
moving
braking
stopped
mixed
unknown
```

Фаза движения определяется по скорости, ускорению и изменению положения.

В первой версии можно реализовать простую эвристику.

---

### 5.7. Поле `features`

Тип:

```text
dict
```

Пример:

```json
{
  "velocity_mean": 120.5,
  "velocity_max": 1789.0,
  "velocity_std": 30.1,
  "current_rms": 0.071,
  "current_max": 0.128,
  "torque_rms": 0.033,
  "torque_max": 0.074,
  "voltage_mean": 305.1,
  "voltage_std": 0.26,
  "temp_mean": 37.0,
  "temp_slope": 0.0,
  "error_count": 0
}
```

---

### 5.8. Поле `risks`

Тип:

```text
dict
```

Каждый риск должен быть числом от 0 до 1.

Пример:

```json
{
  "current": 0.03,
  "torque": 0.02,
  "velocity": 0.3,
  "voltage": 0.01,
  "temperature": 0.0,
  "statusword": 0.0,
  "error": 0.0,
  "statistical_anomaly": 0.12,
  "data_quality": 0.0
}
```

---

### 5.9. Поле `main_causes`

Тип:

```text
list[dict]
```

Список главных причин снижения оценки.

Пример:

```json
[
  {
    "parameter": "current_A",
    "risk_key": "current",
    "risk_value": 0.72,
    "severity": "warning",
    "message": "RMS-ток повышен относительно допустимого уровня."
  }
]
```

Если состояние нормальное, список может быть пустым.

---

### 5.10. Поле `explanation`

Тип:

```text
list[str]
```

Пример:

```json
[
  "Ошибки привода отсутствуют.",
  "Температура находится в безопасном диапазоне.",
  "Напряжение DC-шины стабильно.",
  "Токовая нагрузка низкая."
]
```

Объяснение должно быть понятным человеку.

---

### 5.11. Поле `recommendations`

Тип:

```text
list[dict]
```

Пример:

```json
[
  {
    "priority": "medium",
    "action": "Проверить механическую нагрузку и состояние муфты.",
    "reason": "Обнаружен повышенный ток при малой скорости."
  }
]
```

При нормальном состоянии рекомендация:

```json
[
  {
    "priority": "low",
    "action": "Продолжить мониторинг.",
    "reason": "Параметры находятся в нормальном диапазоне."
  }
]
```

---

## 6. Требования к Health Score

Health Score рассчитывается по рискам.

Общая формула:

```text
total_risk = weighted_sum(risks)
health_score = 100 * (1 - total_risk)
```

Значение должно быть ограничено:

```text
0 <= health_score <= 100
```

---

### 6.1. Жёсткие ограничения Health Score

Некоторые события должны ограничивать максимальный Health Score.

Примеры:

```text
если error_code != 0:
    health_score <= 40

если fault_flag == True:
    health_score <= 40

если temperature risk >= 1:
    health_score <= 50

если voltage risk >= 1:
    health_score <= 50
```

Это нужно, чтобы модель не выдала высокий Health Score при наличии аварии.

---

## 7. Требования к классификации состояния

Рекомендуемая логика:

```text
если данных недостаточно:
    state = "unknown"

иначе если error_code != 0:
    state = "critical"

иначе если fault_flag == True:
    state = "critical"

иначе если health_score < 50:
    state = "critical"

иначе если anomaly_score >= 0.75:
    state = "critical" или "warning"

иначе если health_score < 70:
    state = "warning"

иначе если anomaly_score >= 0.50:
    state = "warning"

иначе если health_score < 85:
    state = "observation"

иначе если anomaly_score >= 0.30:
    state = "observation"

иначе:
    state = "normal"
```

Точные пороги должны браться из `thresholds.json`.

---

## 8. Требования к рискам

Каждый риск должен быть в диапазоне:

```text
0..1
```

Где:

- 0 — риска нет;
- 1 — максимальный риск.

Обязательные риски:

```text
current
torque
velocity
voltage
temperature
statusword
error
data_quality
statistical_anomaly
```

В версии 0.1 `statistical_anomaly` может быть равен 0.

---

## 9. Требования к физическим рискам

### 9.1. Current risk

Должен учитывать:

- RMS-ток;
- пиковый ток;
- номинальный ток;
- максимальный ток.

---

### 9.2. Torque risk

Должен учитывать:

- RMS-момент;
- пиковый момент;
- номинальный момент;
- максимальный момент.

---

### 9.3. Velocity risk

Должен учитывать:

- максимальную абсолютную скорость;
- паспортную максимальную скорость.

---

### 9.4. Voltage risk

Должен учитывать:

- минимальное напряжение;
- максимальное напряжение;
- стандартное отклонение напряжения;
- безопасные и критические пределы DC-шины.

---

### 9.5. Temperature risk

Должен учитывать:

- максимальную температуру;
- среднюю температуру;
- тренд температуры;
- безопасный и критический предел.

---

### 9.6. Error risk

Должен быть равен 1, если есть ненулевой `error_code`.

---

### 9.7. Statusword risk

Должен учитывать:

- Fault;
- Warning;
- Operation enabled;
- отсутствие `statusword`.

---

### 9.8. Data quality risk

Должен учитывать:

- пропуски;
- некорректные значения;
- временные разрывы;
- слишком короткое окно;
- отсутствие критически важных полей.

---

## 10. Требования к рекомендациям

Рекомендации должны быть rule-based.

Нельзя подключать LLM.

Рекомендации должны:

- иметь приоритет;
- иметь действие;
- иметь причину;
- соответствовать найденным рискам.

Пример:

```json
{
  "priority": "high",
  "action": "Проверить питание и тормозной контур.",
  "reason": "Обнаружена нестабильность напряжения DC-шины."
}
```

---

## 11. Требования к ошибкам выполнения

Модель не должна падать при:

- пустом окне;
- пропущенном необязательном поле;
- отдельных `NaN`;
- неизвестном режиме;
- неизвестном `statusword`;
- отсутствии статистического профиля.

В таких случаях модель должна:

1. Записать предупреждение.
2. Повысить `data_quality_risk`.
3. Вернуть результат со `state = unknown`, если диагностика невозможна.

---

## 12. Требования к логированию и debug-данным

Результат может содержать поле `debug`.

В `debug` можно положить:

- число точек в окне;
- sampling rate;
- список предупреждений;
- использованные лимиты;
- использованные веса;
- применённые жёсткие правила.

В production-режиме debug можно отключать.

---

## 13. Требования к производительности

Первая версия должна работать быстро на небольших данных.

Ориентир:

- обработка одного окна — меньше 100 мс;
- обработка сессии 60 секунд при 10 Гц — меньше нескольких секунд.

Не нужно преждевременно оптимизировать код, но нельзя делать заведомо неэффективные вложенные циклы на больших данных без необходимости.

---

## 14. Требования к тестируемости

Каждый ключевой модуль должен быть тестируемым отдельно.

Минимальные unit-тесты:

1. Загрузка CSV.
2. Валидация обязательных полей.
3. Расчёт RMS.
4. Расчёт физических рисков.
5. Расчёт Health Score.
6. Классификация `normal`.
7. Классификация `critical` при `error_code != 0`.
8. Формирование рекомендации при высоком токе.
9. Обработка пустого окна.
10. Обработка пропусков.

---

## 15. Acceptance criteria

Модель считается реализованной для Version 0.1, если:

1. Есть функция диагностики одного окна.
2. Есть функция диагностики всего CSV.
3. Возвращается JSON-совместимый результат.
4. Health Score находится в диапазоне 0..100.
5. Все риски находятся в диапазоне 0..1.
6. Ненулевой `error_code` даёт `critical`.
7. Нормальная телеметрия даёт `normal` или `observation`, но не `critical`.
8. Пропуски данных не ломают программу.
9. Рекомендации формируются на основе рисков.
10. Код не использует готовые ML-модели.
